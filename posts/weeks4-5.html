    The big realization this week came from the File Inclusion room, and it's changed how I think about web vulns.

    Connecting them all is a single core problem: crappy input validation. Whether it's LFI, SSRF, XSS, SQLi, command injection, the attack vector doesn't change; figure out where user input touches server logic, figure out how said logic works, and then make an input that makes it do something completely different.

    Take Local File Inclusion (LFI) as an example. If an app has an endpoint like http://webapp.thm/get.php?file=hello.pdf, and the backend just does something like:

    $file = $_GET['file'];
include("/var/www/app/" . $file);

    Then you can just visit http://webapp.thm/get.php?file=../../../etc/passwd and suddenly we have a lot more power on our hands. Apparently this is called the "dot-dot-slash attack"—I love it.


    But What If There Are Filters?

    This is where it gets fun. Developers try to protect against this stuff, but if you can figure out how their filters work, you can usually figure out a way around them

    • File extension is hardcoded? Well then input becomes /etc/passwd.php—we can't do anything right? Nah. Just end the string with a null byte: ../../../etc/passwd%00
    • "../" sequences are being removed? Just add more of them: ....//....//file—when they remove the first ../, what's left is still ../../file
    • Certain paths aren't allowed? Put a /. at the end: ../../../etc/passwd/. . It technically requests the contents of /etc/passwd as a directory, which I guess some filters just don't care about.

    So it's really all just logic and rules. If I can figure out the rules, I can pass both the filter AND my goal as a hacker. It's a win-win.


    Putting It Into Practice

    Another challenge used $_REQUEST in PHP, which means it accepts input from both GET and POST. The GET parameter didn't work, but when I sent the same payload via POST with curl, it worked beautifully:

    This module was absolutely packed with new techniques. New additions to the arsenal include:

    File Inclusion Techniques

    LFI: Directory traversal with ../ inputs, null byte injection, various filter bypasses. The key was understanding how include(), require(), and file_get_contents() work in PHP. Another reason to be thankful that I chose LAMP stack for my chat app.

    RFI: Making the server include and execute code from an remote source. Pretty self explanatory. I learned that we need allow_url_fopen and allow_url_include to be enabled in PHP for it to work, but when it does work, it's a straight shot to RCE.

    Server-Side Request Forgery (SSRF)

    SSRF sounds kinda scary, but it's basically just tricking the server into making requests on your behalf. It's kind of self-explanatory. The attack itself reminded me a lot of RFI—just about URL parsing instead of input parsing.

    Let's say there's an endpoint https://website.thm/item/2?server=api which internally requests https://api.website.thm/item?id=2. If I set server=google.com then we get a request to https://google.com.website.thm/item?id=2.

    Wait, but that's kinda useless isn't it? That's what I thought, but no, it just takes a little creativity. If we set server to server=google.com/?x=, the final request becomes: 

    https://google.com/?x=.website.thm/item?id=2
    Everything after the ?x= gets URL encoded and becomes completely irrelevant. Now the server is requesting Google instead of api.website.thm.

    Now that was a pretty mundane example, but what if the intended request contains auth headers or tokens? If we simply redirect that request to our own server, we can capture those credentials. Pretty cool stuff.

    Filter bypasses:

    • What if the whitelist requires website.thm in the target URL? Just register a subdomain like website.thm.prdox.me. Technically it still follows the rules.
    • Blacklist blocks 127.0.0.1 or localhost? Register a subdomain that resolves to those IPs—apparently that's a real thing.
    • Is it being strict about the origin? Look for open redirects like https://website.thm/?redirect=prdox.me. They're oddly common.

    Cross-Site Scripting (XSS)

    I always knew XSS existed, but I never understood how the payload actually reaches other users. Turns out that this is why social engineering is such a big focus of cybersecurity education.

    For example: /?error=<script>alert(1)</script>. You send a malicious link to a victim, they click it, payload executes in their browser. That's an example of Reflected XSS. Of course, there are more types.

    Stored XSS: Payload gets saved to the database somehow (comments, profile info, etc.) and gets executed for everyone who views it. This is what I originally thought XSS was—like how in my old chat app, you could set your username to <p style="color:green">User</p> and it would just embed.

    DOM-based XSS: This one's pretty similar to Reflected XSS, but the payload never touches the server. It's processed entirely in the victim's browser via JavaScript, which means means no WAF can catch it. Cool stuff.

    Blind XSS: This one's like stored XSS, except you can't see it execute—it happens behind the scenes, if you will. THM's example was like in an admin portal where support staff view support tickets. Apparently there's a tool for this: XSS Hunter Express.


    Command Injection

    This one confused me a little bit—not the vuln itself, but how it was different from good ol' RCE. Basically, it's RCE, but specifically when it's shell commands. All command injection is RCE, but not all RCE is command injection. If an app does something like:

    system("ping " . $_GET['ip']);
    You can just add more commands, like 1.1.1.1; whoami or 1.1.1.1; cat /etc/passwd

    Usually command injection isn't very obvious. A good trick for detecting command inectjion is using sleep 5 or ping -c 10: if the response is delayed by exactly that amount then we know we're onto something.

    If certain characters are filtered out of input, I learned that we can try hex encoding: \x2f\x65\x74\x63\x2f\x70\x61\x73\x73\x77\x64 instead of /etc/passwd. Didn't know this, but apparently a lot of programming languages will interpret this no problem, just like that. Pretty useful.


    SQL Injection

    SQLi was the big one. I'd heard of it forever, messed around with it in middle school without really understanding it, but now I actually get how it works.

    Specific techniques I learned were:

    Union-based SQLi: I didn't even know UNION was a thing before this, but it's pretty wild! We can figure out how many columns were in the original query (add null columns one by one to the UNION SELECT until it stops throwing errors). Then: 

    UNION SELECT null,null,database() --append the database name to the results
UNION SELECT null,null,group_concat(table_name) FROM information_schema.tables WHERE table_schema='db_name' --dump all table names
UNION SELECT null,null,group_concat(column_name) FROM information_schema.columns WHERE table_name='users' --dump all column names in a table
UNION SELECT username,password,null FROM users --dump all records from those columns
    Just knowing this exists is a game changer.

    Boolean-based blind SQLi: If you can only see true/false responses (like "username taken"), you can enumerate character by character. SQL has this awesome operator LIKE that allows you to use wildcards: 
    UNION SELECT 1,2,3 WHERE database() LIKE 'a%'  # username isn't taken; first char isn't 'a'
UNION SELECT null,null,null WHERE database() LIKE 'b%'  # not taken
UNION SELECT null,null,null WHERE database() LIKE 'c%'  # username taken! first char is 'c'
UNION SELECT null,null,null WHERE database() LIKE 'ca%' # not taken
UNION SELECT null,null,null WHERE database() LIKE 'ch%' # taken! second char is 'h'
    And so on. Repeat until nothing matches anymore. It's tedious as hell, but it works pretty well.

    Time-based blind SQLi: Basically the same idea; we can put a SLEEP(5) in place of one of the null's and if the page hangs for exactly 5 seconds, the query was true. Same brute-force strategy from there.

    Brute forcing this stuff was starting to get INSANELY annoying by the end of this THM room. As I found out later, there's a tool for exactly this: SQLMap. Yep. That SQLMap. Point it at a vulnerable param, let it run, and it'll find everything it can for you. I'll absolutely be using this for everything going forward (especially during picoCTF).
