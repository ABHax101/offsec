    Introduction

    Hi! I'm alive! It's been a minute—like a really long minute. School is finally over, though, so I officially have no excuse to not hack stuff more often now! I'm looking forward to it. This is going to be a fun writeup, seeing as it's been an entire season since I completed this box. It's ok though—that's why I take notes the way I do. Shouldn't be too bad. Here we go!

    Box Name: Crack The Gate 2
    Platform: picoCTF
    Difficulty: Medium
    Category: Web Exploitation

    This was my first real use of Burp Suite in a real CTF challenge, and it just so happened to be the perfect box to learn it on. Though admittedly, I'd already gotten a head start. Around this point in time, the 'leader' of our pico team (we'll call him Jerry) was checking in with everyone: we'd decided to meet at lunch one of those days so that we could all lock in and do some challenges together. He couldn't help but notice that I was still using curl and the web inspector for everything—he said it was painful to watch. I told him it was working fine, and that I didn't see the problem. Silly me. He had me install Burp Suite right then and there, and he showed me the basics of Interceptor, Repeater, and Intruder—said that those three were the only tabs that I strictly needed, and that I could get familiar with the rest on my own time. That was a pretty helpful head start—this box would have been a lot more painful without it.

    As per the challenge description:

    "The login system has been upgraded with a basic rate-limiting mechanism that locks out repeated failed attempts from the same source. We've received a tip that the system might still trust user-controlled headers. Your objective is to bypass the rate-limiting restriction and log in using the known email address: ctf-player@picoctf.org and uncover the hidden secret."

    Rate limiting. Yay.
    The challenge also provided a passwords.txt file to download. That led me to think that it would be some sort of offline password cracking challenge, where I'd extract some conveniently-placed hash from the source code and finally learn to use hashcat. It wasn't, but the password list was definitely relevant.


    The Login Form

    The login page had a simple form. When I looked at the source, the method attribute wasn't set; a quick look in the client-side JavaScript, though, revealed that it was POSTing to /login with application/json content type.
    I tried a login with random credentials and checked the Network tab to see what it looked like—it was a pretty standard JSON request body with email and password params. Nothing unusual yet.

    Then I tried again. Immediately got locked out:

    "Too many requests. Try again in 20 minutes."

    20 minutes. For one wrong password attempt. Yeah, screw you too. It quickly became clear that a normal brute-force wasn't going to work.

    Understanding the Rate Limiting

    My first bright idea was that the rate limiting might be handled client-side via JavaScript for some reason—it was just a medium box, after all. I tried bypassing it with curl. Same error, though. Clearly the rate limiting was server-side, not something tied to my browser; they were at least kinda doing it properly. Darn.

    My first thought was that maybe it was filtering by IP address—that would be logical. Too many requests from one IP gets that IP locked out. Could I change my IP somehow?

    I tried from my phone, just to make sure that the entire site wasn't locked or something. That one worked. I then connected to a VPN on my laptop and tried again. That one worked too—I could send another request. But somehow I was supposed to change my IP over and over and over again for a brute force attack? Setting up 20 VPN connections could be possible, in theory, but that felt like way too much work for a medium-difficulty CTF challenge, and I might have actually had to pay for that. No thanks.

    I was out of ideas. Time to check the hints.


    One of the hints said "Read more about X-Forwarded-For." That was interesting—sounded oddly familiar.

    What actually is X-Forwarded-For?

    Turns out, X-Forwarded-For is what proxies and load balancers use to forward the original client's IP to the destination server. When a request goes through a proxy, the server would of course normally only see the proxy's IP, not the real client's; XFF gives it a way to preserve that information.

    There's the fun part, though: It's an HTTP header—I can mess around with those. Google said that "Because the X-Forwarded-For header can be easily spoofed by malicious clients sending fake headers, you should never trust the value blindly." After reading that, I knew what I had to do.

    Testing the Theory

    I decided it was time to break out the Burp Suite knowledge that had been shed on me during lunch—my first time using it out in the wild. I sent the POST request to Burp Repeater and added the header: 

    X-Forwarded-For: 1.1.1.1

    I sent it, and prayed. Success—no rate limit error.

    Changed it to 1.1.1.2. Worked again.

    Changed it to 1.1.1.3. Still working.

    Perfect. The server was doing exactly what Google said not to and trusting the X-Forwarded-For header for rate limiting, which meant I could brute force the password list by using a different "IP address" for each attempt.


    Alrighty, time to actually crack this thing! I sent the POST to Burp Intruder—the other tool that Jerry had told me about, but hadn't actually showed me how to use.

    I needed to fuzz two things: the XFF IP addresses and the passwords from the passwords.txt. My initial thought was to use a Cluster Bomb attack—I picked it somewhat arbitrarily, as it said that it allowed for multiple payload sets. But then I looked a little closer and realized that that would send way too many requests. Cluster Bomb tests every possible combination of both sets: if I had 20 passwords and 20 IPs, it would send 400 requests. Not quite what I wanted.

    After a bit of looking around, I found the Pitchfork attack, which would pair up the payloads one-to-one, as in first IP with first password, second IP with second password, third with third, and so on. 20 requests total. Bingo.

    For the IP addresses, I just created a simple text file with 20 arbitrary IPs:

    1.1.1.0
1.1.1.1
1.1.1.2
1.1.1.3
1.1.1.4
...
1.1.2.9

    From what I could tell, the actual IP values didn't matter, and the server didn't seem to be validating them; it was just using them to track rate limiting, and nothing more.

    For the passwords, I simply plugged in the provided passwords.txt.

    From there, I said "here goes nothing," started the attack and watched the responses come in. Since there were only 20 requests, I just manually reviewed them all instead of trying to figure out Burp's filtering options. One of them stood out immediately:

    {
  "success": true,
  "email": "ctf-player@picoctf.org",
  "firstName": "pico",
  "lastName": "player",
  "flag": "picoCTF{xff_byp4ss_brut3_1cc3b76e}"
}

    Hey, cool! That wasn't so bad.


    After what Jerry had showed me, this challenge was a perfect little introduction to actually using Burp in practice, which as it turns out, is a really solid way to learn how it works. Up until Crack the Gate 2, I'd been doing everything with curl and ffuf, which was working fine, but admittedly would have been somewhat tedious for an attack like this one, where I'd have to modify and repeat requests dozens of times.

    Key Takeaways:

    • X-Forwarded-For is a thing, and is often trusted blindly. This one's going into the toolbox—if the server is using this alone for access control, it's trivially bypassable.
    • Burp Repeater is amazingly useful for quick testing. Being able to quickly and cleanly modify a request and immediately re-send it without retyping potentially giant curl commands is a huge quality-of-life improvement.
    • Rate Limiting based on client headers is a REALLY bad idea—spoofing my headers with Burp Suite was unnervingly easy.
    • Burp Suite exists for a reason. Every part of this could have been done with ffuf or a custom script, but Burp made it way easier and more controlled, and put everything that mattered in one place for me. I understand now why pentesters use this as a primary tool—it really is a gamechanger.

    What I'd Do Differently

    Honestly, not much. I wasted an embarrassing amount of time trying the VPN approach and googling around for IP spoofing techniques, but once I saw the hint, everything fell into place in a solid five minutes—it was nothing crazy.

    If anything, I should have stumbled upon XFF in my Google searches earlier—the challenge description literally said "the system might still trust user-controlled headers." That was a pretty clear hint in retrospect.

    Final Thoughts

    This was a pretty satisfying challenge: it felt like it combined multiple skills to exploit a practical, real-world vulnerability, rather than just being a contrived CTF puzzle that forced you down an oddly-specific rabbit hole.

    Plus, I finally got to use Burp Suite—that alone made this challenge worth doing.
