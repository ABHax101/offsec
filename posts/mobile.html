    Introduction

    Hey hey!

    I'm happy to announce that we've tested every bit of the app that was in scope, except for one: the mobile variant.

    Back in 7th grade when I wanted to make Parity mobile apps, my first instinct was to Google how to turn a website into a mobile app. There were plenty of free services online, like Appy Pie and AppMySite and whatnot (note: I'm not affiliated with them in any way), but I guess I didn't like the results or something? I don't know exactly what happened—that was like 5 years ago, after all—but I didn't end up going with any of those free services. I remember trying to rebuild Parity in Android Studio at one point, but that wasn't working too good either—it seemed a lot more complicated than the kind of crap I had going in PHP at the time, so I gave up on that too.

    Eventually, though, I came across Apache Cordova, basically an open-source framework that lets you package regular ol' HTML, CSS, JS into apps for all different platforms, using the operating system's internal browser engine (like Android WebView, for example).

    I really liked that, but there was one problem with it: my entire codebase was in PHP, and I couldn't figure out how to make Cordova work with it. In hindsight, that makes sense—I can't be hosting the entire backend of my app on every mobile device that installs it, that just doesn't work like that.

    My solution? To go into every file in the PHP codebase, strip out all the PHP into separate API files that'd live on my main server, and rewrite the app (almost) from scratch in plain HTML, CSS, JavaScript.

    This should be interesting to look through.

    Let's start with that login.php. First thing's first, check that out:

    <?php
    header("Access-Control-Allow-Origin: *");
    header("Access-Control-Allow-Headers: *");
    $_POST = json_decode(file_get_contents('php://input'), true);
?>

    Right out the gate, this is looking a lot easier to brute force since we're actively turning off CORS. It makes it possible for a Cordova app running from file:// origins to log in, but it also makes it possible for an attacker's cheeky little python script to do the same, a whole lotta times per second. If that attacker hadn't found the SQLi in imageget.php yet, this would be a valid strategy to get user logins.

    I'm getting ahead of myself though—we haven't seen anything beyond the first 5 lines of the file yet...

    Ok, I'm looking at this right now, and remember /index.php? Up at the top of that file, before any of the HTML started, I had the signup and login logic, yes? It seems that in this login.php file, I've literally just copypasted that code from the top and changed a couple things so we could make it work on the mobile app. All the vulns we found in the auth system writeup are still there.

    The only meaningful diffs I see here between this file and /index.php are:

    • login.php doesn't check for duplicate passwords—it doesn't throw that error. That's probably actually a good thing lol
    • Upon successful login, index.php sets the value of the "Username" cookie and redirects the user to /landing.php, whereas login.php simply echoes out Success:whatever_username.

    That's it, just two minor changes. The different success message in login.php, which now contains the user's username, probably has to do with whatever I replaced $_SESSION['Username'] with in the mobile variant, how we're keeping track of that state. We'll look at that in a minute.

    index.html

    Alright, so looking at this bit, it seems like the HTML markup itself is pretty much identical (well, my giant 'description' of the app that I had on /index.php has been replaced with "Welcome to Parity Chatrooms!", but otherwise pretty much identical). The main differences here are in the JS: in the HTML forms, I now have an onsubmit attribute calling functions that POST the contents of each form to /api/login.php.

    The function for the new user form simply POSTs the new user's requested credentials to the API and then puts the response in a div at the top. That response would be either an error message or the "Success! You may log in now" message.

    The function for the existing user form POSTs the user's creds (plaintext btw) to the API. Then, if the response doesn't contain a <div> (which is how we're identifying that there's an error message), then it sets the "Username" cookie according to the content of the success response. As a reminder, that looks like this: Success:whatever_username—if that were the response, then the app would set the Username cookie equal to "whatever_username". If a <div> is found, indicating an error message was returned, then it simply echoes out the response at the top.

    Ok, so we're still doing the Username cookie thing. Check this out:

    if (!cookie.get("Username") == "") {location.replace('landing.html')}

    So pretty much the exact same logic as index.php—meaning the Username cookie bypass should still work. Let's test that real quick.

    Ok, that's actually really interesting! That didn't work in the main PHP app.

    My payload there was simply username=anything'--, and just any random password. My hunch is that it returned an error, just not one of my nicely formatted ones in a div—maybe the raw SQL error text or something like that. So since there was no div, it assumed that the creds were right, and just let me in anyway. Not sure why my username is blank there, though.

    I'm gonna do some digging with Burp Suite real quick.

    Oh! Nope, the response is actually just blank. That's weird. Look:

    Actually, I guess it kinda makes sense. Look at this section of the API code:

    $query = $conn->prepare('SELECT * FROM users WHERE uname=\''.$uname.'\' and pass=\''.$pass.'\'');
$query->execute();
$data = $query->fetch(PDO::FETCH_ASSOC);

    So that query is becoming:

    SELECT * FROM users WHERE uname='anything' --' and pass='whatever'

    So effectively:

    SELECT * FROM users WHERE uname='anything'

    That query returns nothing, because there's no user called "anything"—which means the variable $data will return zero rows.

    The next bit of the PHP looks like this:

    if ($data) {
if ($query->rowCount() > 0) {
    if (($data['uname'] == $uname) && ($data['pass'] == $pass)) {
        $_SESSION['Username'] = $uname;
        echo "Success:".$_SESSION['Username'];
        /* ... */

    It's checking there for if the row count is >0, and only then is it doing any actual checks on the input itself. That if statement has no else block, so the program kinda just dies there, and nothing gets echoed out.

    Hence the completely blank API response. Makes sense now. The app assumes that the lack of a <div> means the login was successful, and sets the Username cookie to whatever the API repsonse says—which explains the blank username.

    Makes sense now.

    Alright, this should be fairly simple. Let's see here...

    The mobile rooms only have five files in them, compared to the main app's ten. That's nice! They are:

    • messages.html - fetches all of the existing messages in this chatroom, using messageget.php, and echoes them out for us.
    • newmessage.html - contains the "new message" textbox and the file input; handles all of the message sending logic, just like the newmessage.phps in the main rooms.

    Apart from writing the report, the capstone project is officially done! Everything within the scope I outlined in that first post, where I did all of my planning for this project, has been audited.

    Now for a short recap of what we found today:

    • More UNION-based SQLi in /api/messageget.php
    • The Username cookie bypass works in the mobile variant as well.
    • The mobile variant allows for SQLi-based login bypass because of how it handles the API response. Fun!
    • landing.html has a call to mpush.php just laying in the page source. While that in itself isn't inherently vulnerable, it's not improbable that a curious attacker would see that and want to try POSTing it themselves—and that's where the problem is. Not as severe of a finding—more pertaining to mpush.php rather than landing.html—but worth noting.
