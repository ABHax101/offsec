    Ok, so here's what I'm seeing right now:

    • I'M ACTUALLY PREPARING MY QUERIES HERE YAY! No SQLi on this layer.
    • Beside from that, there's no input validation of any sort. The input could be like 250MB long and it'll still try to put it into the database.
    • Also on the topic of no input validation: while queries are being prepared, the raw user input that was sent to the server is still being broadcasted as-is to the other users, so maybe possible XSS there depending on how the app displays it. Not confirmed yet but that sounds like something to try.
    • There's not a lick of rate-limiting here. Very easy DoS. The lack of user and/or origin authentication helps with that too.
      • An attacker could just spam messages really quickly. Or, they could amplify it by opening like 1000 clients and then spamming with all of them at once. There's nothing stopping that.
      • If they spam really large messages, like a million emojis at a time or something stupid like that, they all go straight to the database and can eat RAM and storage.
      • For each incoming message we're calling Buffer.from, which has potential to be taxing on the CPU. Right after that, we're running database queries, which can also be really taxing on the CPU. And then, in the callback, we're running Buffer.from again.
      • With hundreds, maybe even thousands or hundreds of thousands of attacker clients open, all spamming at once, an attacker could probably eat all of the server's bandwidth and render it unusable.

    The potato server has one advantage, which is that it's not connected to the database in any way—but everything else still applies to that one too lol. Amazing.

    Alright, I think that's a wrap for this one. Here's what we found:

    • Hardcoded database credentials—which are, in fact, the same credentials that are used in the main PHP codebase as well. So not only hardcoded creds, but credential reuse across literally multiple entire codebases.
    • No auth whatsoever: anyone can connect to the WebSocket servers, from any origin at any time, as long as they know one of the pathnames (which ain't hard to figure out).
    • The WebSocket servers are connected to the database directly with zero validation, so anyone with access to the WebSocket server (i.e. literally anyone lol) can make records in our database of any size and shape. Tens, hundreds of megabytes, maybe even gigabytes at a time, if ws's defaults allow it.
    • User input is being broadcasted verbatim, once again with zero validation, so XSS in the potato room is very very easy to pull off.
    • The WebSocket server is very DoS-able due to a complete and utter lack of rate limiting, everywhere.
    • If one WebSocket server goes down, the keepalive loop for every WebSocket server goes down—not a huge security risk (at least as far as I know, maybe someone could figure something out with that), but still a bug.
