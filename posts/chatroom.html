    Introduction

    This is going to be the biggest session yet: I'm finally auditing the chatrooms themselves.

    There are four chatrooms in this app, and each one of them contains ten files each. Thankfully though, as far as I can see, they're all just copies of each other, and the diffs are only cosmetic. So we really only have to audit ten files today.

    I have no idea what to expect with this one.

    Let's go.


    Ok, actually, remember how I said there were ten files to audit here? Scratch that—only five of them really need attention.

    • messages.php - this is the file that pulls all of the messages for this chatroom from the database and renders them.
    • newmessage.php - this is the file that contains the textbox that users use to send messages, and handles all of the "send message" logic.
    • room.php - this is the big file that ties it all together. It has a frameset with three panels: one for messages.php, one for newmessage.php, and one for sidebar.php (which is a pretty tame file; we won't be going into depth there today). It also handles sending entry and exit messages to chat—like "Welcome, jerry!" and "jerry has left the chat."
    • exitmessage.php - this file is a POST endpoint; you POST it the text "Someone left!" and it sends a push notification to let people know that someone (whatever the value of $_SESSION['Username'] is) left the chat.
    • vc.php - in the sidebar.php, there's a button to open voice chat which adds a new frame to the frameset; this vc.php is the src file for that new frame. This is getting into the voice chat app a little bit, which is out of scope, but I want to include it here because vc.php has a reference to $_SESSION['Username']. Since we've shown that the value of that session var can have unintended effects, I wanna make sure once that we're not exposing the voice chat app to any weird shenanigans by including that there.

    The other five files are:

    • landing.php - this just checks to see if the WebSocket server is reachable, and then redirects you to room.php if it is. There's no funny business in here.
    • log.txt - this is just like the other log.txt we explored a couple sessions ago. Exact same thing, except specific only to this chatroom. We've already covered what you can do to the log.txts in this app.
    • notif.mp3 - the sound that plays to let you know that someone's sent a message when you've navigated away from the app. Nothing here lol.
    • socket.js - the entire file is simply let conn = new WebSocket('wss://ws.parity.nimbusdigital.org/general');. That's the entire thing. This isn't vulnerable, per se—an attacker can find out the WebSocket endpoint in the network tab too. We're not missing anything by not covering it today.
    • sidebar.php - I talked about this one a second ago; it's involved today in that it injects $_SESSION['Username'] into vc.php, but that's literally it. And that's happening when you click on the Voice Channels button on the homepage as well—if you removed this file, literally nothing would change for anyone else in the chatroom. There's no SQL involved, no other funny business. Any potential impact here is only to the self, so it's not all that useful to an attacker.
      • You may have seen a little "Room Warp" thing in the sidebar in previous screen recordings. That's basically just a little feature that allows you to travel between rooms without having to go back to the homepage. It's actually correctly implemented though—user input can't break it because the paths are hardcoded. For the first time, I'm so glad I did that lol.

    Alright, so we've got our work cut out for us in this one. It's looking like $_SESSION['Username'] is going to be a throughline today for pretty much all of this—my bet is more stored XSS with the <img onload=""> trick.

    I think we're ready.


    I'm starting here because I think this is gonna be the quickest to test. The whole file is essentially just one iframe pointed at the voice chat app. Here's what it looks like:

    <iframe id="vc" frameborder=0 allow="camera; microphone; display-capture; autoplay" width=100% height=100% src="https://vc.parity.nimbusdigital.org/join?room=general&name=<?=$_SESSION['Username']?>&audio=1&video=0&notify=1"></iframe>

    Let's look closer at that src:

    https://vc.parity.nimbusdigital.org/join?room=general&name=<?=$_SESSION['Username']?>&audio=1&video=0&notify=1

    It's explicitly setting the name URL param equal to $_SESSION['Username']. That's the username that gets rendered inside of the voice chat room, for everyone who's connected. What happens if we use the img onload trick there in that name field?

    Let's give it a shot. I'll have one "bystander" client in there, just as a control, with username "jerry". Then I'll visit the following URL from a different tab:

    https://vc.parity.nimbusdigital.org/join?room=general&name=<img src='https://google.com/favicon.ico' onload='alert(1337)'>&audio=1&video=0&notify=1

    So in theory, when that client connects, if the voice app isn't correctly configured, then the bystander client will get an alert with content "1337" once our attacker client joins.

    As I said in yesterday's post, the image src url there doesn't actually matter, as long as it's a real image url that'll actually load. We could use pretty much anything there—Google's favicon was just the first image URL I could think of, off the top of my head, that'd be easy to use for testing lol.

    And...

    Check it out! Little bit of scope creep here, but I can confirm that it is possible for the text-chat app to be the root of a problem like this: once again, there's no input validation in the signup form, so it's entirely possible for a rogue $_SESSION['Username'] from my app to enter the voice chat. Scope creep or not, that's still a liability.

    Number of Findings Today: 1

    In my planning, I said that $_SESSION['Username'] is going to be the throughline of today's test, yes? Let's test that.

    I think that <img onload=""> trick we used yesterday (and a second ago) is going to be what makes this work. I have a good (well probably bad, but good as an attacker lol) feeling about this one.

    I'm gonna register a user called <img src=\"https://google.com/favicon.ico\" onload=\"alert(`XSS`)\">. From there, I'm just going to navigate the site like a normal user, nothing crazy. I'll screen record the whole thing—this one's probably gonna get messy.

    Oh, wait, nevermind. Not working—it wont even let me register; it's just reloading the page over and over, not even any errors. Weird.

    AH, wait, that makes sense now lol. I know that for you, as a reader, you read the line above this one like 10 seconds ago, or something like that. Well I wrote it like a solid 15 minutes ago. I've been digging, and I just realized why this isn't working. The users table schema says usernames can't be >50 characters, so the logic in index.php is just silently failing.

    Honestly, that's not even a problem. We're just trying to set $_SESSION['Username'] here right? We've already proven here, as we see in this screen-recording that we can set our $_SESSION['Username'] using the "Username" cookie.

    I've logged back in as jerry. The plan now is simply to change the value of my Username cookie to <img src=\"https://google.com/favicon.ico\" onload=\"alert(`XSS`)\"> rather than registering that as a user.

    Nice! This one's BAD. Once the cookie is set and my $_SESSION['Username'] has taken on its value:

    • room.php embeds the $_SESSION['Username'] into my entry and exit messages
    • newmessage.php embeds the $_SESSION['Username'] into every message I send
    • messages.php inserts every message it pulls from the db straight into innerHTML, so my $_SESSION['Username'] is now embedded into everyone's DOM.

    So basically, I can be a threat just by existing in the chatroom. I said in my very first session, when I was testing the WebSocket server, that XSS didn't seem to be possible in the main chatrooms—I guess I was wrong.

    I have figured out why XSS through messages themselves wasn't working in the main rooms, though. Check out this part of newmessage.php:

    conn.send(/* ... */ + inputField.value.replaceAll(/[\u00A0-\u9999<>\&]/g, function(i){ return '&#'+i.charCodeAt(0)+';' }) + /* ... */)

    Somehow, this was the one place where I actually did escape HTML entities lol. Nice.

    Alright, so we've covered vc.php, and we covered room.php, messages.php and newmessage.php just now. That leaves us with exitmessage.php and then I guess we're done for today!

    This is a pretty small file. Have a look:

    <?php
    session_start();
    if ($_SERVER['REQUEST_METHOD'] === "POST") {
        if (file_get_contents("php://input") === "Someone left!") {         
            require("../../push.php");
            push($_SESSION["Username"]." has left the General room.");
            echo "Done";
        }
    }
?>

    No authentication, nice! We can probably spam the hell out of this one as well. Let's take a look at what that push.php is doing real quick—pretty sure that's what's pinging OneSignal to send push notifications. Here it is:

    <?php
    function push($message = "This is a test notification.") {
        $content = array(
            "en" => $message
        );
        $fields = array(
            'app_id' => "(redacted)",
            'included_segments' => array(
                'Subscribed Users'
            ),
            'contents' => $content,
        );
        
        $fields = json_encode($fields);
        
        $ch = curl_init();
        curl_setopt($ch, CURLOPT_URL, "https://onesignal.com/api/v1/notifications");
        curl_setopt($ch, CURLOPT_HTTPHEADER, array(
            'Content-Type: application/json',
            'Authorization: Basic (redacted)'
        ));
        curl_setopt($ch, CURLOPT_RETURNTRANSFER, TRUE);
        curl_setopt($ch, CURLOPT_HEADER, FALSE);
        curl_setopt($ch, CURLOPT_POST, TRUE);
        curl_setopt($ch, CURLOPT_POSTFIELDS, $fields);
        curl_setopt($ch, CURLOPT_SSL_VERIFYPEER, FALSE);
        
        $response = curl_exec($ch);
        curl_close($ch);
        
        return $response;
    }
?>

    Ok, that's actually kinda funny lol, it's literally just CURLing the OneSignal API. I'm just glad it's exporting a function rather than just pushing whatever the POST body is or something stupid like that.

    Yeah, so as I thought, then—we can probably repeatedly spam "Someone left!" POSTs to exitmessage.php and it'll literally broadcast it to every subscribed user. I can't test this right now because that OneSignal app ID is configured for a different domain (one I don't own anymore), but it's pretty easy to see that that's what would happen.

    Number of Findings Today: 3

    The fact that the OneSignal App ID and API keys are hardcoded in here is pretty awesome too lol. Didn't think we'd get any hardcoded creds today. I stand corrected. Make that 4.

    Number of Findings Today: 4

    WOAH, HOLD IT. Remember how I said it's good that push.php isn't just pushing the POST fields? Well check out /api/mpush.php, the one I built for the "mobile" app:

    <?php
    header("Access-Control-Allow-Origin: *");
    header("Access-Control-Allow-Headers: *");
    function push($message = "This is a test notification.") {
        /* same as the one in `push.php` */
    }

    if ($_SERVER["REQUEST_METHOD"] == "POST") {
        push(file_get_contents('php://input'));
        echo "Success!";
    }
?>

    Right there at the bottom, in that little if block. God dammit.

    Ok, noted, so an attacker can simply POST LITERALLY ANYTHING to https://parity.nimbusdigital.org/api/mpush.php and that POST body will get sent out as a push notification to EVERY SUBSCRIBED USER. That's a hell of a whoopsie right there.

    Hey, I mean, I'll take it.

    A quick recap of our findings today:

    • XSS via $_SESSION['Username'] in the voice chat app. Scope creep or not, a rogue $_SESSION['Username'] from somewhere else in the app is still a liability—and that somewhere else is within scope.
    • Room-wide XSS with $_SESSION['Username'] using the img onload trick—all 3 of the chatroom files work together on that one to make it even more terrible.
    • You can send "left the chat" notifications to everyone who's subscribed to push notifications on this app, simply by POSTing "Someone left!" to exitmessage.php
    • ANYBODY can send completely customized push notifications to every subscriber via /api/mpush.php. Mmmmm.
    • OneSignal credentials are hardcoded in push.php and mpush.php. While those secrets aren't going to be directly exposed to an attacker, since they're inside the PHP, this is definitely still something to keep in mind.

    I guess that's pretty much it for this one. XSS galore!

For what it's worth, I did build that bit at least a good few months after the rest of the chat app's codebase had been established—maybe we'll get lucky and not find much funny business there.
